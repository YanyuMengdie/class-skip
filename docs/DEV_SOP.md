# 逃课神器开发模式 SOP（四档版）

> 基于 GPT 的双模式建议改进,核心修订:
> - 增加 "Think First" 和 "Quick Fix" 两档,补上中间地带
> - 判断标准从 "改哪个文件" 改为 "改坏了用户能不能立刻感知"
> - 增加 "不确定时默认升一档" 的反自我欺骗机制
> - 修正了 "出问题直接 revert" 的过度简化

---

## 一、为什么要分四档

我有四种不同的真实需求,过去用一套流程导致两个极端:
1. 大重构时不够谨慎,改坏过核心
2. 小 bug 修复时流程太重,失去做产品的快感

GPT 提出双模式抓到了核心矛盾,但只分两档不够用:
- 改个按钮 ≠ 改一行 service 层
- 修一个明确的 bug ≠ 探索一个新功能的设计
- 想清楚一件事 ≠ 写代码做一件事

所以我用四档:

```
Think First    →  纯产品/认知问题,不写代码,只在网页版讨论
Playground     →  实验性、视觉性、可以删的东西,在 branch 里玩
Quick Fix      →  明确范围的 bug 和小改动,直接修但要测
Core           →  架构性、跨模块、有数据流影响的改动,完整 SOP
```

---

## 二、判断档位的方法

不要看"改哪个文件",看下面三个问题:

1. **改坏了用户会不会立刻受影响?**
   - 是 → Core 或 Quick Fix
   - 否 → Playground

2. **改动范围我现在能不能说清楚?**
   - 能说清楚单点 → Quick Fix
   - 牵涉多模块/数据流 → Core
   - 连改什么都还没想好 → Think First

3. **改对了用户能感知的提升大不大?**
   - 大但风险高 → Core
   - 小但稳定 → Quick Fix
   - 不确定 → Playground 先试

### 反自我欺骗铁律

人会在疲惫时把 Core 当 Quick Fix,在兴奋时把 Quick Fix 当 Core 写文档累死自己。

**不确定档位时,默认升一档。**
- 不确定是 Playground 还是 Quick Fix → 当 Quick Fix
- 不确定是 Quick Fix 还是 Core → 当 Core
- 这样判断模糊时偏保守,保护项目主干

## 三、四档详细规则

### 档位 1:Think First / 想清楚再说

#### 适用范围
- 产品流程层的根本问题(比如"学习流程到底是什么")
- 还没有明确解法、只有模糊痛感的事
- 多个改动方案在打架、需要先选方向
- 涉及用户认知模型的设计决策

#### 目标
不是写代码,是把脑子里的混乱整理出来。

#### 流程
1. 只在 Claude 网页版讨论
2. 不开 branch、不动代码、不让 Claude Code 介入
3. 产出物:`docs/thinking/<日期>_<主题>.md`
4. 文档里写:
   - 问题是什么
   - 几种可能的方向
   - 每种方向的代价和收益
   - 暂定方向(可以是"再观察一段时间")

#### 结束标志
想清楚之后,这个任务**升级**为 Core 或 Quick Fix,或者被废弃。

#### 红线
- 不允许在 Think First 阶段动代码
- 不允许"想着想着顺手改一下"

---

### 档位 2:Playground / 爽模式

#### 适用范围
- UI 样式、卡片布局、按钮文案
- 视觉优化、小动画
- 空状态页面、onboarding 文案
- 新功能 demo(还不接入真实数据流)
- 产品感觉测试、交互草稿
- mock 数据页面

#### 判断关键
**改坏了不会立刻影响用户**——因为它在 branch 里,主干没动。

#### 目标
- 快速看到效果
- 快速获得产品感觉
- 保留创造快感
- 不污染主干

#### 流程
1. 开新 branch:`playground/<主题>`
2. 可以让 Claude Code 自由发挥(因为反正能删)
3. 边改边看效果,不写 inquiry 文档
4. 改完后做**结束动作**:
   - 满意 → 整理后合并 main
   - 不满意 → 显式删 branch:`git branch -D playground/xxx`
   - 部分有价值 → 抽出有用的部分,然后删 branch

#### 红线
- 不允许 Playground branch 长期挂着不管
- 不允许直接合并未经整理的 Playground 代码进 main
- 不允许在 Playground 改动里碰 service 层、persistence、prompt 等核心
  (碰了说明你判断错档位了,升级到 Quick Fix 或 Core)

---

### 档位 3:Quick Fix / 快修模式

#### 适用范围
- 已知的明确 bug,症状清楚
- 单点修复,影响范围可以一句话说清楚
- 文案错误、逻辑小错、明显的视觉问题
- 不涉及架构改动、不引入新数据结构

#### 例子(我项目里的实际场景)
- 便签字号 +/- 按钮失效
- 略读模式下上传 PDF 报错
- 某个按钮点了没反应
- 某个状态显示不对

#### 目标
- 不写一份完整 inquiry 文档,但要把修复做扎实
- 测试不能省、commit message 不能糊弄

#### 流程
1. 在 Claude 网页版**简短**讨论:
   - 复现步骤是什么
   - 根因可能在哪
   - 改哪个文件、哪个函数
2. 不需要写 `docs/inquiries/UPDATE_*.md`,但要在对话里有上面三件事的明确答复
3. 给 Claude Code 简短指令:
```
   修复 <bug 简述>
   症状:...
   预期定位:...
   要求:
   - 先告诉我你打算改什么、改在哪一行
   - 我确认后再动手
   - 不要顺手改其他地方
```
4. Claude Code 列计划 → 你确认 → 改 → 你手动测 → commit
5. commit message 写清楚:
```
   fix: <bug 一句话描述>
   
   症状:...
   根因:...
   修复:改了 <文件>:<函数>
```

#### 红线
- 不允许"顺手重构"
- 不允许跳过手动测试
- 修第一次没修对 → revert 这次尝试,**回到讨论阶段重新分析**,不是放弃整个 bug
- 如果发现根因比预想复杂(牵涉多模块) → **升级到 Core**,不要硬塞进 Quick Fix

---

### 档位 4:Core / 核电站模式

#### 适用范围
- AI streaming、PDF parsing、retrieval、prompt orchestration
- 精读/略读核心数据流
- 备考工作台核心逻辑
- IndexedDB/localStorage 持久化层
- 全局 state management
- API service 层
- 数据结构变更
- 大规模重构
- 跨多个核心文件的修改
- 新核心功能(比如区域阅读、模式融合)

#### 目标
不是追求快,而是追求:
- 不炸
- 可测试
- 可回退
- 不引入隐藏 bug
- 不让 AI 自作主张

#### 流程

##### 阶段 1:Claude 网页版策略会
- 讨论当前代码现状
- 讨论痛点根因
- 列出几种改动方案,各自代价
- 选定方案并说明理由

##### 阶段 2:写 inquiry 文档
产出 `docs/inquiries/UPDATE_<日期>_<主题>.md`,必须包含:
- 背景(为什么要改)
- 改动范围(哪些文件、哪些行号区间)
- **不改什么**(重要——划定边界)
- 验证清单(改完要测哪几个场景)
- 回退预案(出问题怎么撤)

##### 阶段 3:Claude Code 执行
开场指令:
```
请按 docs/inquiries/UPDATE_<日期>_<主题>.md 实施本次更新。

铁律:
1. 严格按文档的"改动范围"和"不改什么"执行
2. 每动一个独立改动,做一个独立 commit
3. 任何不确定、任何意外发现,停下来报告,不要自作主张
4. 改动开始前先列计划(要改哪些文件、哪些行号),等我确认

现在请先:
- 阅读 docs/inquiries/UPDATE_<日期>_<主题>.md
- 阅读 CONTEXT.md 了解当前项目状态
- 列出你计划修改的所有文件和具体位置,先给我看
```

##### 阶段 4:列计划 → 你确认 → 一改一 commit
- Claude Code 列出"我打算改这些",你扫一眼确认
- 确认 OK 才说"开始动手"
- 每完成一个独立改动:
  1. Claude Code 报告"完成了 X"
  2. 你跑 `npm run dev`,手动测验证清单
  3. 测通过 → commit + push
  4. 测没通过 → 让 Claude Code 修,**不要进入下一个改动**

##### 阶段 5:本地测试
基础冒烟清单(每次必跑):
- [ ] `npm run dev` 启动无报错
- [ ] TypeScript 编译无错误
- [ ] 上传一个 PDF,进入精读模式正常
- [ ] 切到略读模式正常
- [ ] 进入备考工作台正常
- [ ] 笔记本能打开

然后跑本次改动的专属验证清单。

##### 阶段 6:更新文档
回到 Claude 网页版,告诉它:
- 这次改了什么
- 测试过了什么
- 有没有意外发现

让它帮你:
- 更新 `CONTEXT.md`(如果项目结构或关键事实有变化)
- 更新 `CHANGELOG.md`
- 归档 `docs/inquiries/UPDATE_*.md`
- 如果发现了原本认知错误,加进 CONTEXT.md 的"产品事实修正"

#### Core 模式红线
- 不允许 AI 自由发挥
- 不允许一次改很多不相关文件
- 不允许边想产品边改核心代码
- 不允许跳过测试
- 不允许在凌晨 3 点做核心需求
- 不允许"顺手重构"
- 不允许把 Think First 没想清楚的问题混进 Core 任务

## 四、回退预案

### Quick Fix / Core 单次 commit 出问题
```bash
git revert HEAD
git push
```
然后**回到讨论阶段重新分析**,不是放弃整个修复目标。

### Core 一系列 commit 出问题
```bash
git revert <最新commit> <次新commit> ...  # 按倒序
git push
```

### Playground 整个 branch 不满意
```bash
git checkout main
git branch -D playground/<主题>
```

### 整个改动方向错了
回到 Think First 档,承认方向错了,重新设计。
不要在错误方向上继续改。

## 五、应用到当前的六条改动

作为示范,我用四档分类一下我现在手头的六条:

| # | 内容 | 档位 | 理由 |
|---|---|---|---|
| 1 | 融合递进阅读和略读模式 | Think First → Core | 先想清楚"递进阅读"指什么、融合后的交互是什么,再进 Core |
| 2 | 略读下上传别的 PDF 出错 | Quick Fix | 已知 bug,复现路径清楚 |
| 3 | 学习流程没弄明白 | Think First | 纯产品认知,不动代码 |
| 4 | 区域阅读(选页略读)新功能 | Core | 新功能、涉及 PDF parsing + 状态管理 |
| 5 | 精读批量加载崩溃 → 一次性预生成 | Think First → Core/Quick Fix | 先搞清楚崩溃根因是 rate limit 还是内存,再决定方案档位 |
| 6 | 便签笔记字号失效 | Quick Fix | 已知 bug,代码定位明确 |

按这个分类,我应该先做的是:
- Quick Fix:6(便签字号) → 2(略读上传)
- Think First:5 的根因调查 → 3 的学习流程梳理 → 1 的递进阅读定义
- Core:4(区域阅读)等其他想清楚后再排

## 六、这套规则的核心精神

- **承认快感是正当需求**:Playground 存在的意义就是让我保留做产品的爽
- **承认想不清楚也是状态**:Think First 存在的意义就是允许我先不写代码
- **分档不是为了限制自由,是为了保护主干**:让低风险的事快、高风险的事稳
- **判断标准是影响范围,不是文件位置**:同一个文件里,改 toolbar 样式是 Playground,改 onUpdateAnnotation 是 Core
- **不确定时升一档**:对抗自我欺骗
- **revert 是中止尝试,不是放弃目标**:bug 该修还得修,只是换个路径
